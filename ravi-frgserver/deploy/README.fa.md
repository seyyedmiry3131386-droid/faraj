# راهنمای نصب، کارتابل و بهره‌برداری

این راهنما برای **یک سرور لینوکس**، یک فرایند Node و یک دیسک محلی است. دریافت مرکزی فقط در `server.mjs` پیاده شده است؛ `npm run dev`، خروجی Worker و سایت استاتیک فقط حالت مرورگری دارند. نصب‌کننده مرکز را با `CENTRAL_ENABLED=0` خاموش می‌گذارد؛ در این حالت «ثبت» به معنای دریافت توسط کارتابل نیست. تا تکمیل چک‌لیست، سامانه را فقط برای دادهٔ ساختگی و در شبکهٔ محدود استفاده کنید.

این نصب روی سرور مقصد، DNS و دستگاه بلهٔ واقعی اجرا نشده و ممیزی امنیتی مستقل، اسکن بدافزار و ظرفیت عملیاتی تأیید نشده است. قبل از پذیرش اطلاعات واقعی، مسئول فنی و مالک داده باید مراحل و محدودیت‌های زیر را بپذیرند. ثبت در این پروژه **ارسال خودکار به هیچ سامانهٔ رسمی دیگری نیست**.

## ۱. دامنه، زیردامنه و HTTPS

1. در پنل DNS، رکورد `@` دامنهٔ `frgserver.ir` را به IP عمومی **واقعی سرور مقصد** وصل کنید. برای کارتابل یک رکورد `admin` از نوع A به همان IP، یا CNAME به نام عمومی مورد تأیید مدیر DNS، بسازید. مقدار IP قدیمی یا نمونه را بدون تأیید مالک سرور استفاده نکنید. رکورد `www` اختیاری است.
2. برای بررسی روی کامپیوتر خود یا سرور اجرا کنید: `nslookup -type=A frgserver.ir` و `nslookup -type=A admin.frgserver.ir`. نتیجه باید IP مورد انتظار را نشان دهد؛ نام‌سرورهای دامنه، TTL، چند رکورد A/AAAA و نتیجهٔ مرورگر بیرونی را نیز بررسی کنید. انتشار DNS ممکن است زمان ببرد. وجود کنترل پنل DNS به تنهایی اثبات دسترسی عمومی نیست.
3. اگر ساخت `admin.frgserver.ir` ممکن نیست، از مدیر DNS یک نام HTTPS **جداگانه** مثل `staff.example.org` بگیرید و مقدار `ADMIN_ORIGIN` و `server_name` مربوط به ادمین در Nginx را هماهنگ عوض کنید. مسیر `/admin` روی همان مبدأ جایگزین این جداسازی نیست. پنل را در صورت امکان فقط از VPN یا IPهای سازمان در دسترس بگذارید.
4. پورت‌های ۸۰/۴۴۳ باید از بیرون برای صدور و استفاده از گواهی قابل دسترسی باشند؛ پیش از تغییر فایروال، دسترسی SSH را حفظ کنید. پس از نصب و انتشار DNS، روی سرور نمونهٔ زیر را اجرا کنید و تأییدیه‌های Certbot را بخوانید:

   ```sh
   sudo certbot --nginx -d frgserver.ir -d admin.frgserver.ir --redirect
   ```

   اگر نام ادمین فرق دارد همان نام واقعی را جایگزین کنید. فقط اگر `www` نیز واقعاً به این سرور اشاره دارد و لازم است، `-d www.frgserver.ir` را اضافه کنید. تمدید خودکار گواهی، زنجیرهٔ گواهی و هر دو نشانی را در مرورگر بررسی کنید. نمونهٔ Nginx صرفاً نقطهٔ شروع است و در این محیط با Certbot/Nginx واقعی آزموده نشده است.

## ۲. نصب جدید

- از پروژهٔ استخراج‌شده، `sudo bash deploy/install.sh` را اجرا کنید. این اسکریپت با یافتن مسیرهای نصب قبلی متوقف می‌شود و به‌صورت خودکار فایروال را تغییر نمی‌دهد. از قبل از اطلاعات، Nginx و تنظیمات سرور نسخهٔ پشتیبان بگیرید.
- Node.js نسخهٔ ۲۲ یا بالاتر در `/usr/bin/node` و npm سازگار لازم است. نسخهٔ مخزن پیش‌فرض اوبونتو ممکن است قدیمی‌تر باشد؛ نصب مطمئن نسخهٔ لازم و سازگاری بسته‌ها با سیستم‌عامل بر عهدهٔ مدیر است. نصب‌کننده با نسخهٔ قدیمی متوقف می‌شود. معماری و کتابخانهٔ سیستم باید با binary بستهٔ SQLite سازگار باشد؛ اسکریپت یک آزمون بازکردن پایگاه انجام می‌دهد.
- وابستگی‌های تولید با lockfile و `npm ci --omit=dev --ignore-scripts` نصب می‌شوند؛ `better-sqlite3` نسخهٔ قفل‌شده برای Linux x64/arm64 رایج binary همراه دارد. این روش دانلود ناخواستهٔ header و اجرای اسکریپت نصب بسته‌ها را حذف می‌کند، نه نیاز به بررسی منشأ و به‌روزرسانی امنیتی آن‌ها را.
- فایل‌ها در `/opt/ravi`، تنظیمات در `/etc/ravi.env`، سرویس در `ravi.service` و داده در `/var/lib/ravi` هستند. `systemctl status ravi`، `sudo nginx -t` و `curl http://127.0.0.1:4173/healthz` را بررسی کنید. فرایند Node عمداً فقط روی loopback گوش می‌دهد؛ Nginx باید تنها proxy مورد اعتماد آن باشد و `X-Real-IP` و `X-Forwarded-Proto` را خودش بازنویسی کند.
- نصب‌کننده کلید API خارجی یا مدل نصب نمی‌کند. در صورت استفاده از مدل داخلی یا سرویس گفتار، تنظیم و صحت آن‌ها جداگانه لازم است. سرویس‌های مدل را فقط روی loopback/VPN قرار دهید؛ پورت‌های داخلی Node، مدل و گفتار را به اینترنت باز نکنید.

## ۳. کلید و توکن خصوصی

هیچ توکن، رمز، کلید داده یا URI برنامهٔ احراز هویت را در چت، Git، گزارش خطا، log، آرگومان خط فرمان یا فایل عمومی قرار ندهید. دستورات زیر برای نصب **جدید** هستند و نباید کلید موجود را جایگزین کنند؛ از پایانهٔ قابل اعتماد استفاده کنید.

```sh
sudo install -d -o root -g ravi-web -m 750 /etc/ravi
# noclobber از جایگزینی فایل قبلی جلوگیری می‌کند
sudo bash -c 'set -euo pipefail; umask 027; set -o noclobber; openssl rand -base64 32 > /etc/ravi/data.key'
sudo bash -c 'set -euo pipefail; umask 027; set -o noclobber; read -rs -p "Bale bot token: " token; echo >&2; printf "%s\n" "$token" > /etc/ravi/bale.token; unset token'
sudo chown root:ravi-web /etc/ravi/data.key /etc/ravi/bale.token
sudo chmod 640 /etc/ravi/data.key /etc/ravi/bale.token
```

توکن باید متعلق به **همان بازویی** باشد که مینی‌اپ را اجرا می‌کند. روی `/etc/ravi.env` با `sudoedit` این مقادیر را قرار دهید، ولی فعلاً مرکز را تا ساخت حساب‌ها و تکمیل آزمون‌ها فعال نکنید:

```ini
APP_ORIGIN=https://frgserver.ir
ADMIN_ORIGIN=https://admin.frgserver.ir
CENTRAL_DATA_DIR=/var/lib/ravi
CENTRAL_DATA_KEY_FILE=/etc/ravi/data.key
BALE_BOT_TOKEN_FILE=/etc/ravi/bale.token
CENTRAL_ENABLED=0
```

فایل تنظیمات باید `root:root` و `0600` بماند. دسترسی خواندن فایل‌های دو راز برای کاربر سرویس از گروه `ravi-web` لازم است. **کلید داده را گم یا عوض نکنید**: گزارش‌ها، فایل‌ها و اطلاعات TOTP موجود با کلید جدید قابل خواندن نیستند و migration/چرخش کلید خودکار پیاده نشده است. کلید را جدا از پشتیبان در مخزن اسرار با دسترسی و بازیابی کنترل‌شده نگه دارید. تغییر توکن بازو نیز امضاهای قبلی را نامعتبر می‌کند. ساعت سرور و دستگاه‌های TOTP باید همگام باشند.

## ۴. حساب مسئولان

ابتدا مطمئن شوید `/var/lib/ravi` به کاربر `ravi-web` تعلق دارد؛ systemd با `StateDirectory=ravi` آن را ایجاد می‌کند. هر فرد باید حساب جدا، رمز تصادفی طولانی و برنامهٔ TOTP خودش را داشته باشد. با پایانهٔ تعاملی و بدون ذخیرهٔ خروجی در log:

```sh
sudo -u ravi-web env CENTRAL_DATA_DIR=/var/lib/ravi CENTRAL_DATA_KEY_FILE=/etc/ravi/data.key /usr/bin/node /opt/ravi/staff-cli.mjs add admin.one admin
sudo -u ravi-web env CENTRAL_DATA_DIR=/var/lib/ravi CENTRAL_DATA_KEY_FILE=/etc/ravi/data.key /usr/bin/node /opt/ravi/staff-cli.mjs add reviewer.one reviewer
```

نام‌ها مثال‌اند؛ نام کاربری ۳ تا ۶۴ کاراکتر کوچک لاتین و رمز ۱۴ تا ۲۵۶ کاراکتر است. ابزار رمز را دوبار بدون نمایش می‌پرسد و یک URI حاوی کلید TOTP می‌دهد. کلید `secret` را در برنامهٔ احراز هویت همان مسئول ثبت کنید؛ URI را مانند رمز محافظت کنید و در هیچ log یا اسکرین‌شات مشترکی قرار ندهید. نقش `reviewer` به همهٔ گزارش‌ها دسترسی دارد؛ نقش `admin` علاوه بر آن log دسترسی را می‌بیند. تفکیک پرونده‌ها بر اساس واحد/منطقه و ارجاع کار هنوز وجود ندارد.

برای فهرست، به‌جای `add ...` از `list`، برای بازیابی حساب از `reset username` و برای قطع دسترسی از `disable username` استفاده کنید، با همان سه متغیر/مسیر دستور بالا. `reset` رمز و TOTP تازه می‌دهد، حساب را فعال و همهٔ نشست‌هایش را باطل می‌کند؛ `disable` نیز نشست‌ها را باطل می‌کند. ورود کارتابل رمز + TOTP، سقف تلاش و نشست با انقضای بیکاری دارد. محدودیت تلاش در حافظهٔ یک فرایند است و با راه‌اندازی مجدد پاک می‌شود؛ VPN، محدودیت proxy و ممیزی امنیتی همچنان لازم‌اند.

پس از تأیید DNS/TLS، حساب‌ها، پشتیبان، سیاست داده و شبکه، `CENTRAL_ENABLED=1` را در `/etc/ravi.env` بگذارید و `sudo systemctl restart ravi` کنید. خروجی `https://frgserver.ir/api/config` باید `"central":true` نشان دهد؛ `https://admin.frgserver.ir/` صفحهٔ ورود کارتابل باشد. شکست سرویس را با `systemctl status ravi` بررسی کنید، نه با نمایش رازها. `CENTRAL_ALLOW_INSECURE_DEV` فقط برای آزمون داخلی است و نباید روی سرور در معرض شبکه تنظیم شود.

## ۵. داده، حریم خصوصی و محدودیت‌ها

- سرور `initData` خام بله را با توکن بازو و زمان امضا بررسی می‌کند؛ پیش‌فرض سقف عمر `BALE_MAX_AUTH_AGE_SECONDS=7200` است. این مقدار در مدت اعتبار مانند یک گواهی حامل قابل بازپخش است؛ آن را در log، URLهای اشتراکی یا ابزار تحلیل ثبت نکنید. `via=bale` و `initDataUnsafe` مدرک هویت نیستند. شناسهٔ حساب بله در گزارش رمزگذاری می‌شود و برای مسئول مجاز قابل مشاهده است؛ این شناسه تأیید نام واقعی یا شمارهٔ تلفن اظهاری نیست. دسترسی به سرویس‌های مدل در حالت مرکزی نیز امضا می‌خواهد.
- سرور Node برای صفحهٔ عمومی CSP با اجازهٔ اسکریپت از خود دامنه و `https://tapi.bale.ai` می‌دهد؛ کارتابل CSP سخت‌گیرانهٔ جدا و جلوگیری از قرارگیری در iframe دارد. برای سازگاری مینی‌اپ، iframeکردن صفحهٔ عمومی محدود نشده و script رسمی بله شخص ثالث مورد اعتماد است. سازگاری CSP و WebView را در آزمون واقعی بررسی کنید؛ این سربرگ جای ممیزی امنیتی یا محافظت در برابر نفوذ به SDK را نمی‌گیرد.
- متن گزارش، شناسهٔ تأییدشده، نام فایل و فایل با AES-256-GCM رمزگذاری می‌شوند. SQLite با WAL/FULL و sync فایل و دایرکتوری روی فایل‌سیستم محلی استفاده می‌شود. شناسهٔ دریافت، زمان، وضعیت، نام حساب مسئول، رخدادهای دسترسی، اندازه و برخی metadata پایگاه رمزگذاری کامل دیسک نیستند. امنیت در برابر مدیر سرور، نفوذ زمان اجرا، کلید افشاشده، خرابی سخت‌افزار یا بکاپ بدون کلید تضمین نشده است.
- پیش‌نویس، پیوست‌های انتخابی و در صورت موفقیت، نسخهٔ گزارش ثبت‌شده در IndexedDB همان مرورگر بدون رمزگذاری اختصاصی برنامه باقی می‌مانند. کاربر باید خطر دستگاه مشترک و پیامد پاک‌کردن دادهٔ سایت، به‌ویژه از دست‌رفتن امکان بازیابی ارسال در انتظار، را بداند. سازوکار حذف انتخابی و نگهداری محلیِ قابل تنظیم در این نسخه وجود ندارد.
- سقف هر ارسال ۱۰ فایل و مجموع ۱۰۰ MiB است؛ محدودیت پسوند/MIME اسکن محتوای بدافزار نیست. دانلود به‌صورت attachment/octet-stream است، اما مسئول باید پیش از بازکردن، فایل را طبق سیاست سازمان در محیط ایزوله و با ابزارهای مناسب بررسی کند. اسکن خودکار و قرنطینهٔ بدافزار در این بسته پیاده نشده‌اند.
- بعد از تأیید سرور رسید `RV-…` را نگه دارید. کارتابل با این رسید جست‌وجو و وضعیت را تغییر می‌دهد؛ نمایش عمومی وضعیت، اعلان، ارجاع پرونده و یکپارچگی با مرجع بیرونی وجود ندارد. ارسال مجدد همان کلید و محتوای ثابت دوباره ثبت نمی‌شود؛ ثبت مجدد با کلید جدید یا پاک‌شدن دادهٔ مرورگر ممکن است گزارش تکراری بسازد. هنگام پاسخ گم‌شده، پیش از ویرایش یا شروع دوباره «بررسی وضعیت» را بزنید.
- کل سامانه تک‌سرور/تک‌فرایند است. SQLite/WAL و پوشهٔ فایل‌ها را روی NFS یا بین چند instance استفاده نکنید. سهمیه و هشدار مصرف دیسک، تعداد اتصال، پشتیبان خارج از سرور، retention و فرایند حذف/درخواست داده باید پیش از انتشار تعیین شوند؛ حذف مدیریتی و سیاست نگهداری خودکار در این کد پیاده نشده است. log نمونهٔ Nginx مسیر و query را ثبت نمی‌کند، ولی IP و زمان دارد؛ سایر logها و retention را نیز بررسی کنید.
- قطع معمول آپلود فایل‌های موقت آن را پاک می‌کند؛ با خاموشی یا crash ممکن است فایل رمزگذاری‌شدهٔ ناقص در `incoming` یا پوشهٔ رمزگذاری‌شدهٔ بدون ردیف ثبت‌شده در `objects` باقی بماند. پاک‌سازی پس از crash خودکار نیست. ظرفیت دیسک را پایش کنید و پیش از هر پاک‌سازی دستی، سرویس و همهٔ پردازه‌های مرتبط را متوقف، نسخهٔ پشتیبان تهیه و تطبیق با پایگاه را به مسئول فنی بسپارید؛ هرگز پوشه‌های `objects` را صرفاً بر اساس ظاهر یا هنگام کار سرویس حذف نکنید.

## ۶. پشتیبان و بازیابی

ابزار از SQLite در حال اجرا snapshot آنلاین می‌گیرد و سپس فایل‌های رمزگذاری‌شدهٔ تغییرناپذیر را کپی می‌کند. آپلودهای ناتمام و نشست‌ها در snapshot نیستند؛ کلید نیز داخل پشتیبان نیست. مثال، فقط پس از آماده‌سازی مقصد امن و سنجش ظرفیت:

```sh
sudo install -d -o ravi-web -g ravi-web -m 700 /var/backups/ravi
BACKUP="/var/backups/ravi/$(date -u +%Y%m%dT%H%M%SZ)"
sudo -u ravi-web env CENTRAL_DATA_DIR=/var/lib/ravi /usr/bin/node /opt/ravi/backup-cli.mjs "$BACKUP"
```

مقصد باید جدید و خارج از دادهٔ زنده باشد؛ ابزار روی مقصد موجود نمی‌نویسد. پشتیبان و کلید را جداگانه با کنترل دسترسی، نسخه‌گذاری و نسخهٔ خارج از سرور نگه دارید. هشدار شکست و کمبود فضا لازم است. نسخهٔ پشتیبان، اطلاعات و حساب‌ها را تا زمان snapshot برمی‌گرداند، نه تغییرات بعدی را.

**بازیابی را ابتدا روی سرور آزمایشی با دادهٔ ساختگی انجام دهید.** روند نمونه روی همان سرور، پس از آماده‌شدن برای قطعی و انتخاب پوشهٔ سالم پشتیبان: سرویس را با `sudo systemctl stop ravi` متوقف کنید؛ `/var/lib/ravi` فعلی را با نام زمان‌دار حفظ کنید؛ پوشهٔ جدید `/var/lib/ravi` با مالک `ravi-web` و مجوز `0700` بسازید؛ محتویات پشتیبان انتخاب‌شده را با `cp -a` در آن کپی و مالکیت را برای `ravi-web` تنظیم کنید؛ کلید **همان snapshot** و تنظیمات فایل‌محور را فراهم کنید. سپس ابتدا در محیط محدود سرویس را شروع و سلامت پایگاه، بازشدن گزارش آزمایشی، دانلود فایل و کارتابل را بررسی کنید. نشست‌های قبلی نباید کار کنند. حساب‌هایی که پس از snapshot غیرفعال یا reset شده‌اند ممکن است در snapshot قدیمی باشند؛ دسترسی‌ها را با فهرست مرجع تطبیق دهید و در صورت نیاز همهٔ حساب‌ها را reset/disable کنید. پیش از بازگشت به سرویس عمومی، از دست‌نرفتن گزارش‌های بعد از snapshot و سیاست اطلاع‌رسانی مطمئن شوید.

آزمون خودکار این مخزن بازیابی snapshot با اطلاعات ساختگی، کنترل کلید اشتباه، بازکردن پیوست و حذف نشست را پوشش داده است؛ **بازیابی و پایش روی سرور عملیاتی شما هنوز تأیید نشده‌اند**.

## ۷. مدل‌ها و سرور CPU با حدود ۸ گیگابایت RAM

مدل‌ها همراه بسته نصب و در این سرور واقعی آزموده نشده‌اند. `qwen3:8b` به‌علاوهٔ Whisper و سیستم‌عامل ممکن است در ۸ گیگابایت جا نشود یا کند شود؛ در اینجا تعداد هسته و ظرفیت هدف اندازه‌گیری نشده است. ابتدا مرکز را بدون مدل روشن و آزمون کنید؛ سپس مدل زبانی و گفتار را جداگانه و با دادهٔ آزمایشی بسنجید، فشار حافظه/RSS، زمان پاسخ و خطای هم‌زمانی را ثبت کنید و فقط در صورت کفایت هر دو را با هم فعال کنید. نقطهٔ شروع محافظه‌کارانه `LLM_MAX_ACTIVE=1`، `STT_PROXY_MAX_ACTIVE=1` و `STT_MAX_PENDING=1` است، اما این سقف‌ها مانع اجرای هم‌زمان **یک** درخواست هر مدل نمی‌شوند و تضمین حافظه نیستند. مدل کوچک‌تر ممکن است جا شود ولی دقتش باید جداگانه سنجیده شود. مدل‌های واقعی small/medium گفتار و مدل زبانی ۰٫۶B در محیط دیگری سنجیده شده‌اند، نه ۸B روی این سرور: [`evaluation/LOAD_REPORT.fa.md`](../evaluation/LOAD_REPORT.fa.md).

## ۸. پذیرش پیش از استفادهٔ واقعی

1. دسترسی جداگانه و HTTPS معتبر برای هر دو دامنه، انتقال رمز/توکن فقط در کانال امن، VPN پنل، ساعات سیستم و تمدید گواهی را تأیید کنید.
2. با خود بازوی بله و گوشی واقعی طبق [`BALE_MINIAPP.fa.md`](../BALE_MINIAPP.fa.md)، مجوزها، انتخاب فایل، لینک تماس اضطراری، امضای صحیح و غلط، انقضا، قطع ارتباط، رسید یکتا و ورود هر مسئول را با دادهٔ ساختگی آزمون کنید.
3. ممیزی مستقل امنیتی، کنترل آسیب‌پذیری وابستگی‌ها، سنجش بدافزار پیوست، خط‌مشی مجوز دسترسی/نگهداری/حذف، تهیه و بازیابی عملی پشتیبان و مانیتورینگ فضای دیسک را تکمیل کنید.
4. مدل‌های واقعی و هم‌زمانی پیش‌بینی‌شده را روی همان CPU/RAM و با صدای فارسی واقعیِ دارای متن مرجع اندازه بگیرید؛ دقت نام، عدد، پلاک، نویز و زمان پاسخ را با معیار پذیرش کارفرما بسنجید. نتیجهٔ آزمون‌های ساختگی و نمونه‌های کوچک تضمین کیفیت واقعی نیست.
5. به‌روزرسانی، پاسخ به رخداد، مسئول شیفت، روش بازیابی در خرابی سرور و محدودیت‌های کارتابل را با مالک سامانه مستند کنید. در صورت شکست هر مورد، اطلاعات واقعی دریافت نکنید.
